Nuclear equipment drawing change-detection system

The aim of Doosan Enerbility is to find the changes between two revisions of its nuclear equipment drawings automatically. I built the VLM layout-detection module, which divides each sheet into views, tables, and text, and decreased the latency of diff detection. I also built the web app on a PostgreSQL task queue. The project is in development, and deployment is near.

  • 95.5%layout-detection recall on 40 held-out pages (F1 93.2)

Why a pixel diff does not work

For each change, the system reports a category (added, deleted, or modified), a one-line description, and a box on both sheets. A pixel diff cannot do this:

  • Elements move. Views, tables, and notes change position, and some sheets are redrawn. A table that only moved is not a change.
  • Three kinds of content. A dimension, a table cell, and a note change in different ways. Each needs its own comparison.

Thus the pipeline divides each sheet into regions. Then it compares a view with a view and a table with a table. This design sets my two threads of work. Layout detection must find every region. Diff detection must be fast, because one comparison makes dozens of VLM calls.

My contribution

The team has four people. My work had two main threads and one smaller part:

  • Layout detection, end to end. I built the rendering, the VLM call and its prompt, and the geometric post-processing. I also designed the evaluation.
  • Comparison latency. I found the bottleneck and removed the work that did not change the answer. I tested each change against fixed accuracy limits.
  • Concurrent comparisons. Before, a user could run only one comparison at a time. I built the Next.js web app and moved comparisons to a PostgreSQL job queue. Workers take jobs from the queue, so several comparisons run at the same time.

I also helped design the architecture of the diff-detection agent. The team built that agent, the region matching, the ground-truth labels, and the end-to-end evaluation.

Layout detection: find every region

If layout detection misses a region, diff detection never sees it. Thus recall was the main target.

For stricter thresholds, I changed the scoring. Annotators leave margins of different sizes. On a 10 pt line, a margin difference of 3 pt decreases IoU to about 0.63. Thus I removed the whitespace from both boxes before I calculated IoU.

In the team’s end-to-end evaluation on 16 drawing pairs, only 1 of 149 missed changes came from layout detection.

Detect layout in one VLM call, then fix geometry in code

Constraint
To tell a view from a table or a note, the model must often understand the drawing, not only its shapes. Each page had a time budget of 60 seconds.
Options considered
OpenCV candidates; clusters of the PDF vectors and text; a pretrained layout detector; a multi-pass pipeline that tiles, parses, merges, and verifies; one VLM call plus code.
Choice
One call returns only the type and the box of each region, in a strict JSON schema. The model transcribes no text. The prompt states the ground-truth labelling rules, so detection and evaluation use one definition. Code does the tasks that geometry can decide (step 3).
Trade-off
The post-processing follows the ground-truth conventions, and it must change if they change. When the model reasons for a long time, a page can take up to about 76 seconds.
Outcome
OpenCV candidates and the PDF text layer could not reach the target recall. The estimate for a multi-pass design was above the time budget.

Fix the remaining errors with examples and ink, not a second call

Constraint
The remaining errors were boundary and grouping errors. The model divided one view into several regions. Its text boxes followed cell borders, but the ground-truth boxes were tight on the letters.
Options considered
A refinement pass on 200 DPI crops; more detailed grouping rules; a second call that only merges views; examples plus deterministic snapping.
Choice
Three cached example pages go before the target page. Each example shows the correct view boxes and a caption that explains the grouping. For text, code renders the page at 4,800 px, removes long strokes such as cell borders, and groups the remaining glyphs into lines. Each box shrinks to its lines plus 5 pt at most.
Trade-off
The examples add about 23,000 input tokens and 2.7 seconds per page. Some view errors remain, because the ground truth groups stacked details differently on different pages.
Outcome
At IoU 0.9, F1 increased from 84.1 to 88.5 (+4.4, 95% CI 3.1 to 5.7, two runs of 124 pages). The refinement pass returned its hint boxes almost unchanged. Stricter rules and a grouping call merged views that must stay separate.

Comparison latency: 30% less time per drawing pair

Remove the work that could not change the answer

Constraint
Profiling showed that diff detection used about 90% of the time. Regions run in parallel, so the slowest region sets the time for the pair. In 6 of 10 pairs, the slowest region was a table or a view.
Options considered
Sixteen combinations: 6, 3, 2, or 1 model calls per view; full or short table answers; a retry or the first answer when the model flags a table as not comparable.
Choice
Tables return only the changed cells, not each cell with a reason. A table flagged as not comparable keeps its first answer. In the logs, a retry never changed that result, because the cause was the method that marks cells on the image. Views get 3 model calls, not 6.
Trade-off
The two largest tables now time out at 120 seconds. Before, one of them finished in about three minutes and found most of its changes.
Outcome
I accepted an option only if recall decreased by 2 points or less and F1 by 3 points or less. A confidence bound also had to exclude larger decreases. Limits of 2 or 1 view calls failed this test.

Shorter answers did not decrease accuracy. On the 122 tables that both arms finished, F1 was 0.770 in each arm. Most of the F1 increase comes from tables that no longer fail. Diff detection uses an LLM, so small differences between single runs can be noise.

What I learned

Output tokens set the latency. Thus the least expensive speed-up was to stop the models from writing text that nobody reads, such as transcriptions and unchanged table cells.

A retry helps only if a failure is random. Only profiling showed me that these failures were not random.

Next, I will measure the queue under real load after deployment. I will also test a longer time limit for the largest tables only.
