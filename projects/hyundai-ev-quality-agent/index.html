Why domain knowledge must live outside the code

Field engineers ask the same types of question again and again. The correct way to answer each type is domain knowledge, not code. At first, this knowledge was in the agent prompts, so each change needed a developer and a release.

I think that this structure fails over time in every agent. The field changes, and new question types appear. The harness and the knowledge of the agent then drift away from the work. Developers do not own the domain, and the domain owners usually do not write code.

So the people who know the domain must maintain the knowledge outside the code. I designed the agent around this split: the code reads the knowledge, and domain people edit it as data.

My contribution

Hyundai Motor Group builds the multi-agent platform. My MakinaRocks team built the query agent, which answers from a relational database, a graph database, and a document lake. Its Text-to-SQL agent is the main agent of the platform.

I designed and built four parts:

  • Skill system. The skill-selection middleware in the Text-to-SQL agent, and the system that PMs use to manage the skills.
  • Harness agent. The orchestrator that wraps an agent on the platform.
  • PPTX subagent. The agent behind the slide and report tools of the harness agent.
  • Evaluation framework. A library, a CLI, and an API server that score agents and gate CI on thresholds.

Skills that PMs manage

I turned the frequent question types into 50 predefined skills. Each skill has a description, which tells when the skill applies, and instructions, which tell the agent how to answer.

Keep skills as data, not as prompt text

Constraint
PMs know how to answer each question type. Developers control the agent code and its releases.
Options considered
Write the rules in the agent prompt; hard-code a path for each question type; or let the model select from managed skills.
Choice
Skills are managed data outside the agent code. PMs change the content. Developers change only the mechanism.
Trade-off
The selection quality depends on the descriptions. When the list becomes longer, PMs must keep the descriptions distinct.
Outcome
PMs improve the answers to common questions without a developer release.

A harness agent that adds capabilities

The harness agent wraps an agent on the platform, for example the query agent. It adds memory, documents, messages, and safety checks, but simple questions must not become slower.

  • Short-term memory. The thread state stays in a PostgreSQL checkpoint. When the loop context goes above a token budget, old tool results change to a short marker.
  • Long-term memory. After each answer, a background task extracts facts and preferences into a wiki. Users can also save and delete memories with tools. The wiki search uses pgvector and has a time limit. Memory is isolated for each user and each agent.
  • Middleware chain. Around each model call, middleware repairs tool calls that a restart left without results. It puts the wiki context immediately before the latest user message and stops parallel tool calls.

Reports straight from the conversation

Users can tell the harness agent to write the conversation into a PPTX report. The report tools call the PPTX subagent. The model does not write code or XML. It fills typed specs for 13 slide layouts and 30 chart types, and python-pptx builders draw them on PPTX templates. Structural checks return each layout error as a tool result with the field and the limit, so the model corrects its own output.

To make reports faster, I decreased the number of tool and model calls. The subagent now writes the pages in parallel and retries only the refused pages.

Evaluation in each agent’s CI

Each agent team on the platform must check its agent in CI before deployment. A team adds my evaluation framework with a config and a gold dataset. Several agents on the platform now run it in their CI pipelines.

  • Metrics. 14 metrics in three groups: RAG, Text-to-SQL, and common quality.
  • Config. A YAML file identifies a LangGraph graph, maps its final state to common fields, and sets a threshold for each metric.
  • Gate. The command exits with 0 on a pass, 1 if the gate fails, or 2 on a config error.
  • Delivery. A CLI, a FastAPI server with 12 metric endpoints, and a Docker image.

Code for objective answers, a judge only for subjective quality

Constraint
An LLM judge is not reliable on objective tasks. A large SQL result set does not fit in a judge prompt. Gold datasets are small.
Options considered
Judge every answer with an LLM; match SQL strings; or compare result sets and retrieved document IDs in code.
Choice
Code checks objective answers. Text-to-SQL uses Soft F1 on (column, value) facts between the predicted and gold result sets. RAG compares the retrieved document IDs with the gold IDs. A judge scores only subjective quality and groundedness. For small samples, the report gives Wilson intervals, cluster-robust standard errors, and bootstrap p95 values.
Trade-off
Each item needs a prepared gold result set. Correct SQL that returns a different shape gets a lower score.
Outcome
The pass or fail on correctness is reproducible and does not depend on a model’s opinion.

Limits and next steps

I did not measure the routing accuracy, the latency that the harness agent adds, or the effect of the skills on answers. The 70% share of turns without tools is a design estimate, not a measurement.

Tools in the loop can lose the harness state and fall back to the last configuration. Under concurrent use, one thread can then get the settings of another thread.

I recommend two next steps. First, gate CI on the lower confidence bound, not on the point estimate. Second, add a rendered check to the PPTX loop. Now no step looks at the rendered slides, so problems that the structural checks miss go to the user.
