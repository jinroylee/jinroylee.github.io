AI video-generation server stabilisation project

Automation Server 2.0 turns a keyword, product URL, or document into a generated video. I built its Docs2Video pipeline and fixed its scaling problems — a rate limiter shared across pods, isolated FFmpeg workers, and locking that ended lost jobs.

Problem

The server uses LLMs, web crawlers, and generative AI to produce a video script, images, and background footage, then assembles them into a video. It needed to handle large volumes of external API calls and CPU-heavy video work, never lose a job, and stay stable under heavy load.

What I built: Docs2Video

When a user uploads a PPT, PDF, or document, the pipeline extracts its text and images. An LLM uses that content to design the video’s structure and write the script. The video is then assembled from the extracted images together with newly generated images that match the content.

Key decisions

One rate limit, shared by every pod

External APIs enforce RPM and TPM limits, but each pod only knew about its own traffic. I wrote a rate-limit queue backed by Redis Pub/Sub so all pods share one limit. Calls are counted in a 5-second sliding window, and each pod combines the shared channel information with its own state to decide whether to run a task.

Result: zero 429 (rate limit exceeded) errors during large-scale API use.

Isolate CPU-bound FFmpeg work

Prometheus showed CPU usage spiking, and FFmpeg tasks bottlenecked when the existing Agenda queue processed them in bulk. I moved FFmpeg tasks to a separate BullMQ queue with concurrency 1 and a hostname check, so each pod runs only one FFmpeg job at a time.

Result: overall job processing more than 30% faster.

Serialise job creation with Redlock

When many jobs were registered at once, some were lost before they reached the Agenda queue. I introduced Redis-based Redlock: the lock is acquired just before a job is created and released just before it is enqueued, which serialises jobs on their way into the queue.

Result: lost jobs eliminated.

Validation

I designed a Puppeteer-based UI load test on EC2 m4.2xlarge instances, each running four PM2 processes with four browsers, simulating 2,000 requests per hour for two hours. The server stayed stable and the new queues behaved correctly; the job processing rate stayed above 95% and the failure rate below 1%.
