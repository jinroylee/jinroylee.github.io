Wind-turbine electrical-schematic troubleshooting agent

Nordex field engineers troubleshoot turbine faults with electrical schematics of hundreds of pages. I built a builder pipeline that turns the schematic PDF and XML export from EPLAN, the engineers' design software, into a knowledge graph. A PostgreSQL store precomputes the wiring, and an agent answers through a fixed set of tools and never writes SQL. The project is in development.

  • ~0.1 sper wiring trace: one recursive SQL query over the walk layer
  • 10 / 16test questions answered as designed in a local demo, one run per question

Reading an EPLAN drawing

Many field questions are about wiring: what feeds this fan, or what loses power when a breaker trips. The electrical drawing has the answers, but it is not data. Before I could model it, I learned how EPLAN draws and exports a circuit.

  • The PDF. This drawing has 418 pages: circuit diagrams, a single-line overview, and generated reports such as terminal diagrams and parts lists. The PDF contains no wires or pins, only strokes, shapes, and text at positions. But EPLAN writes bookmarks, title blocks, and report tables into it. These tell which items exist and where.
  • The XML export. It lists each connection from end to end. It has no page numbers or part data. My export was one revision newer than the printed sheet.
  • The engineer. The engineer measures with a meter after reading the answer. A wrong pin is worse than “unknown”, and each value must cite its place on the sheet.

I put this knowledge into a schema with 18 entity kinds, 82 fact kinds, and 24 invariants.

My contribution

This is a team project. The team owns the fault-diagnosis agent and its guardrail. I owned all of the EPLAN work:

  • the readers for the PDF and the XML export
  • the knowledge-graph schema and the builder
  • the PostgreSQL store, its walk layer, and the comparison of three databases
  • the drawing agent and its seven tools, which run as a subagent tool inside the team’s agent
  • a local demo that builds a graph from an uploaded drawing and answers questions about it

I also tuned the team’s LLM judge for diagnosis paths. I put the reason before the label in its output schema and graded each field independently. On 35 chain paths, overall accuracy increased from 65% to 75%, chain accuracy from 64% to 81%, and cause accuracy from 75% to 92%.

From drawing to knowledge graph

The builder uses deterministic rules and no vision model. Two runs on the same input give byte-identical files.

An entity is only a kind and its printed name. Every other claim is a fact with four stamps: evidence, band (Sure or Weak), applicability, and citation. So the graph never guesses, it labels uncertain data, and it keeps both values when two sources disagree.

The export confirmed 30,215 facts and changed 462 Weak facts to Sure. I also compared the wire-end names with a wire list that I used only in development. Where both ends of a wire were Sure, 98.1% agreed.

Electrical potential as the walk layer

The fact graph splits the wiring into very small steps. One wiring question can cross thousands of facts, and each tool must apply the electrical rules again on its own. I used a basic rule of circuits to make a smaller layer. Conductors that join with no contact between them are at one electrical potential. Only a contact, a breaker pole, or a disconnect terminal can separate two potentials.

At load time, the store joins conductors into potentials and records each contact, pole, and terminal as a crossing. About 88,000 facts become 2,595 potentials and 1,166 crossings. A wiring question is now a walk from potential to potential. One trace is one recursive SQL query and takes about 0.1 s. The four wiring tools read this layer, so they use one set of electrical rules.

PostgreSQL, not a graph database

Constraint
A walk has no fixed length. It must stop at a busbar, a load, or a pin-unknown end, and a trace must stop after 8 contacts.
Options considered
Apache AGE (Cypher on PostgreSQL), Neo4j, or plain PostgreSQL with recursive SQL. I measured all three.
Choice
Plain PostgreSQL with the walk layer. AGE could not stop variable-length paths early, and its queries reached 20 s timeouts. Neo4j needed the paid edition for high availability, online backup, and enterprise sign-in.
Trade-off
In my benchmark, Neo4j traced faster: 5–7 ms against 11–57 ms. If an electrical rule changes, the store must build the walk layer again.

An agent that answers by walking the wiring

The model does not write SQL or the values in an answer. It selects one of seven tools and gives the user’s words to it. Code resolves the name, walks the wiring, and attaches citations. Each tool runs fixed, read-only SQL with a timeout.

Explain, Find, and Page look up devices, text, and sheets. Slot shows the ports of a card. The other three tools answer by logic, one crossing at a time:

  • Trace walks back from a load to the source that feeds or switches it.
  • Impact walks forward from a breaker pole and collects each load that loses power when the breaker trips.
  • Measure recommends the point halfway between the last good point and the first bad point. It puts power-off checks before power-on checks.

Code checks the typed answer of the model and builds the blocks: a card, a chain, an impact tree, or the next measurement. If the check fails two times, the agent gives a fixed, safe reply. For questions that the drawing cannot answer, such as alarm codes, a fixed answer tells the user where to look.

The median turn took 10.4 s. The tools took 8–720 ms, and model calls used the rest. Both misses were tool-selection errors on class phrases such as “the fans in the second cabinet”. The model gave a printed name to the tool, not the user’s words. With those words, the trace tool returned the expected chain. The weak point is now the tool selection, which changes from run to run.

Status and next steps

The system runs only as a local demo, and field engineers do not use it yet. Only one drawing has a graph, and I checked each fix with one run. The reader rules depend on the EPLAN layout of the PDF, so a different template can break them with no error. The engineers’ schema review and the hosting are not done.

Most of the work was to decide what the graph can claim, not to parse. Next, I will add repeated runs of the scenario questions, build a graph for a second drawing, and give alarm-code questions a separate path.
