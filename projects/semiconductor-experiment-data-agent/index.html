The whole stack inside an air-gapped network

Jusung Engineering makes manufacturing equipment for semiconductors, displays, and solar cells. In a government-funded programme, MakinaRocks built an agent that answers questions about experiment reports and HR policies.

The customer’s network has no internet connection. We could not use a hosted model or download a package. Each model, database, and service had to run on the customer’s Kubernetes cluster and its fixed GPUs. Two of us delivered every layer of the stack inside that network, from LLM serving to deployment.

My contribution

The team had two people. I owned these parts:

  • Serving and platform. I served both models on vLLM. I set up the vector, relational, and object stores and the deployment environment on the cluster.
  • Structuring. I designed the DDL schema. I built the transformation from parsed slide tables to header-addressed rows, and the VLM image descriptions.
  • Ingestion architecture. I designed the queues and workers and tuned the full pipeline.
  • Retrieval. I built the experiment-report retrieval paths of the agent.

My teammate built slide parsing, the NAS scan, decryption, de-duplication, the HR-policy agent, the offline packaging, and the chat and admin features.

Reading the structure of a slide report

Before I designed the schema, I studied how years of slide decks on a DRM-protected NAS carry their meaning. Three properties controlled the design:

  • Layout. Layouts are free. People split tables by hand and put graphs on top of table cells.
  • Meaning. Most of the content is tables and numbers. A value has no meaning without its row and column headers. These headers are often nested on both axes.
  • Questions. Engineers ask for conditions, not topics: “have we ever run this deposition at pressure X?”

A good answer must come from the correct cells of the correct slide. One rule controls my design: the LLM makes judgements, and code builds the structure.

Address cells by their headers

Constraint
A cell needs its full header path to have a meaning, and the table layout changes from slide to slide.
Options considered
Index tables as Markdown in the slide text; have an LLM map each table to a fixed schema; store cells with header paths.
Choice
An LLM only marks which rows and columns are headers. Code then builds each header path, such as “pressure > chamber”, stores the paths of the table as a catalog, and gives each cell one row path and one column path. Rule-based heuristics split the two most important table types, recipes and run sheets, into one record for each step or run.
Trade-off
Ordinary tables depend on a correct header decision by the LLM. The agent can reach only the tables that a slide refers to. The heuristics fit only the known formats.
Outcome
Retrieval selects the header paths that a question needs, and reads only those cells.

Where vector search fell short

Because the reports use a narrow vocabulary of process terms and units, one query returned dozens of similar slides. Two versions of the same question, with the same conditions in a different order, also retrieved very different slides.

First, I made retrieval stable. The LLM divides each question into five identity facets, such as equipment and film, and its conditions. Fixed rules make query variants from the facets. Reciprocal rank fusion (RRF) merges the hybrid-search results of all variants. Now two versions of a question with the same facets run the same queries. The cost is one more LLM call for each question.

Answer run-sheet questions with two Text-to-SQL steps

Constraint
Run sheets contain one experiment run per row, and the questions filter on numbers, such as runs above 350 °C at 5 Torr. Vector similarity cannot evaluate “above”.
Options considered
Vector search on cells, or one Text-to-SQL query on the full schema.
Choice
Each run is a row, and its cells carry the header paths from the catalog of the table. The first query selects the runs that meet the conditions. The second query fetches only the cells that the question asks for, such as film thickness.
Trade-off
Two LLM calls, and correctness depends on the header catalog. Only run sheets get this path.
Outcome
The database, not the model, evaluates numeric conditions.

Recommendation. Vector search is a weak primary retriever for numeric reports with a narrow vocabulary. I wrote a recommendation for a table-first design: tables and Text-to-SQL as the primary path, with vector search as support. The tables can come from the customer’s experiment-management software, or from reports that load into a stricter schema.

Finding the bottlenecks by testing

The report archive holds about 20 TB of PPTX files, and the first ingestion design was too slow for this volume. I ran the pipeline on real reports to find each bottleneck. Then I changed the layer that caused it: the Kubernetes pod structure, the processes and threads in each worker, or the vLLM serving flags.

Split ingestion into stage workers

Constraint
One process for each file, with threads only for LLM calls, was too slow, and LibreOffice slide capture added time. More multiprocessing caused out-of-memory errors and overflowed the database connection pool.
Options considered
Tune processes and threads inside one service; split the work by stage.
Choice
Move CPU-heavy rendering and latency-bound LLM calls from the main worker to separate pods. Four chained queues connect the pods. Parsing workers write records to disk, and one writer loads them into PostgreSQL in batches through PgBouncer.
Trade-off
There is no real message broker, and the queue hierarchy is complex.
Outcome
Each stage scales independently. Database writes go through one writer, not through each parsing process.

Remove the processes that the OOM killer left

After the split, worker memory increased over time, but no task reported an error. I compared the server logs with the memory curve. The processes that the OOM killer hit became orphans with no error message, and they kept their memory. I added a memory sweeper that finds and removes these orphans. The sweeper only treats the symptom: the nested subprocesses of the rendering step still cause orphans.

Result

Throughput increased from about 10–20 report files per hour to about 150. Two years of reports loaded in about a week and a half. At the old rate, the estimate for this load was about two months.

Limits and lessons

I did not measure retrieval accuracy or answer accuracy. The throughput figures are for the full pipeline, not for each change. The evidence on answer quality is qualitative, and GPT-OSS-120B often did not follow its system prompt.

On-prem LLMs removed per-token cost. But latency became the new budget, and faithfulness was not guaranteed. My main lesson is to use the LLM only where the logic cannot be deterministic. Next time, I will plan resources and parallelism before I build the first worker.
