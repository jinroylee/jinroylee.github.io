Nordex 풍력발전기 전기 도면 기반 고장 대응 에이전트

노르덱스의 현장 엔지니어는 수백 쪽짜리 전기 회로도를 보며 터빈 고장에 대응합니다. 전기 엔지니어들을 위한 소프트웨어 (EPLAN) 에서 내보낸 도면 PDF와 XML 파일을 이해하여 지식 그래프로 바꾸는 builder pipeline 을 구축하였습니다. 배선을 미리 계산해 두는 PostgreSQL 저장소와, SQL을 직접 쓰지 않고 정해진 도구로 답하는 에이전트도 개발했습니다. 현재 개발 중입니다.

  • 87,975418쪽 도면에서 만든, 출처가 붙은 fact
  • ~0.1 s배선 추적 1회 (walk layer 위 재귀 SQL 한 번)
  • 10 / 16로컬 데모 1회 실행에서 설계대로 답한 테스트 질문
역할
도면 파싱, 지식 그래프 스키마, 그래프 저장소, 도면 에이전트와 도구

EPLAN 도면 읽기

현장 질문 중 상당수는 배선에 관한 것입니다. 이 팬은 어디서 전원을 받는지, 차단기가 트립되면 무엇이 꺼지는지 같은 질문입니다. 답은 전기 도면에 있지만 도면은 데이터가 아닙니다. 모델링에 앞서 EPLAN이 회로를 어떻게 그리고 내보내는지부터 익혔습니다.

  • PDF: 이번 도면은 회로도, 단선도, 단자도/부품 목록 같은 자동 생성 리포트를 합쳐 418쪽이었습니다. PDF에는 전선도 핀도 없고, 선, 도형, 좌표 위의 텍스트만 있습니다. 대신 EPLAN이 북마크, 표제란, 리포트 표를 함께 써 넣기 때문에 어떤 장치가 어디에 있는지는 알 수 있습니다.
  • XML export: 모든 연결이 양 끝까지 들어 있지만 쪽 번호와 부품 정보가 없습니다. 제가 받은 export는 도면보다 revision이 하나 앞서 있었습니다.
  • 엔지니어: 엔지니어는 답을 보고 바로 계측기를 듭니다. 틀린 핀을 알려 주느니 “모름”이 낫고, 모든 값은 도면 위 위치를 출처로 가져야 합니다.

이렇게 파악한 내용을 entity 18종, fact 82종, 불변식 24개로 된 스키마로 정리했습니다.

My contribution

팀 프로젝트였고, 고장 진단 에이전트와 가드레일은 팀이 맡았습니다. EPLAN과 관련된 일은 전부 제가 맡았습니다.

  • PDF와 XML export를 읽는 reader
  • 지식 그래프 스키마와 빌더
  • PostgreSQL 저장소와 walk layer, DB 3종 비교
  • 도면 에이전트와 도구 7개 (팀 에이전트 안에서 subagent 도구로 실행)
  • 도면을 올리면 그래프를 만들고 질문에 답하는 로컬 데모

팀의 진단 경로 LLM judge도 튜닝했습니다. 출력 스키마에서 판단 이유를 라벨보다 앞에 두고, 항목마다 따로 채점하게 바꿨습니다. 체인 경로 35개에서 전체 정확도는 65% → 75%, 체인은 64% → 81%, 원인은 75% → 92%로 올랐습니다.

도면에서 지식 그래프로

빌더는 비전 모델 없이 결정적 규칙으로만 동작합니다. 같은 입력으로 두 번 실행하면 바이트 단위로 같은 파일이 나옵니다.

entity에는 종류와 도면에 찍힌 이름만 둡니다. 나머지 주장은 전부 fact이고, fact마다 근거, 확신도(Sure 또는 Weak), 적용 조건, 출처가 붙습니다. 이 구조 덕분에 그래프는 추측하지 않고, 불확실한 값에는 라벨을 붙이고, 두 자료가 충돌하면 두 값을 모두 남깁니다.

export로 fact 30,215개를 확인했고, Weak 462개를 Sure로 바꿨습니다. 전선 끝 이름은 개발에만 쓴 배선 목록과도 비교했습니다. 양 끝이 모두 Sure인 전선은 98.1%가 일치했습니다.

전위 기반 walk layer

fact 그래프는 배선을 아주 잘게 쪼개 둡니다. 배선 질문 하나가 fact 수천 개를 거치고, 그대로 두면 도구마다 전기 규칙을 따로 적용해야 합니다. 저는 회로의 기본 성질로 더 작은 레이어를 만들었습니다. 접점 없이 이어진 도체는 모두 같은 전위에 있고, 두 전위를 가를 수 있는 것은 접점, 차단기 극, 단로 단자뿐입니다.

적재할 때 저장소가 도체를 전위 단위로 묶고, 접점/차단기 극/단로 단자를 crossing으로 기록합니다. 약 88,000개의 fact가 전위 2,595개와 crossing 1,166개로 줄었습니다. 배선 질문은 이제 전위에서 전위로 건너가는 walk가 됩니다. 추적 한 번은 재귀 SQL 쿼리 하나이고 약 0.1초가 걸립니다. 배선 도구 네 개가 모두 이 레이어를 읽기 때문에 전기 규칙도 한 벌만 관리하면 됩니다.

그래프 DB 대신 PostgreSQL

제약
walk는 길이가 정해져 있지 않고, 모선이나 부하, 핀 모름 끝에서 멈춰야 합니다. 추적은 접점 8개를 넘으면 멈춥니다.
검토한 대안
Apache AGE(PostgreSQL 위의 Cypher), Neo4j, 재귀 SQL을 쓰는 일반 PostgreSQL. 셋 다 직접 측정했습니다.
선택
walk layer를 둔 일반 PostgreSQL을 골랐습니다. AGE는 가변 길이 경로 탐색을 중간에 멈출 수 없어 20초 타임아웃이 났고, Neo4j는 고가용성, 온라인 백업, 기업용 로그인에 유료 에디션이 필요했습니다.
감수한 비용
벤치마크에서 추적은 Neo4j가 더 빨랐습니다(5~7 ms 대 11~57 ms). 전기 규칙을 바꾸면 walk layer를 다시 만들어야 합니다.

배선을 따라가며 답하는 에이전트

모델은 SQL을 쓰지 않고, 답에 들어가는 값도 쓰지 않습니다. 도구 7개 중 하나를 고르고 사용자의 말을 그대로 넘길 뿐입니다. 이름 해석, 배선 탐색, 출처 첨부는 코드가 합니다. 도구마다 정해진 읽기 전용 SQL을 시간 제한을 걸고 실행합니다.

설명, 찾기, 쪽 도구는 장치, 문구, 도면 쪽을 찾아 보여 주고, 슬롯 도구는 카드의 포트 구성을 보여 줍니다. 나머지 세 도구는 crossing을 하나씩 건너며 논리적으로 답을 찾습니다.

  • 추적: 부하에서 거슬러 올라가 전원을 공급하거나 스위칭하는 지점까지 탐색
  • 영향: 차단기 극에서 아래로 내려가며 차단기가 트립될 때 전원이 끊기는 부하를 수집
  • 측정: 의심 경로에서 마지막 정상 지점과 첫 이상 지점의 중간을 다음 측정 지점으로 제안, 전원을 끈 상태의 점검을 먼저 배치

코드는 모델이 정해진 형식으로 돌려준 답을 검사하고 카드, 체인, 영향 트리, 다음 측정 지점 같은 블록을 만듭니다. 검사에 두 번 실패하면 정해진 안전한 답으로 끝냅니다. 알람 코드처럼 도면으로 답할 수 없는 질문에는 어디를 봐야 하는지 정해진 답을 줍니다.

턴당 응답 시간 중앙값은 10.4초였고, 도구는 8~720 ms, 나머지는 모델 호출 시간이었습니다. 실패한 두 건은 모두 “두 번째 캐비닛의 팬들”처럼 종류를 가리키는 표현에서 나온 도구 선택 오류였습니다. 모델이 사용자의 말 대신 도면에 찍힌 이름을 넘겼습니다. 같은 말을 추적 도구에 직접 넣으면 기대한 체인이 나왔습니다. 이제 약점은 실행마다 달라지는 모델의 도구 선택입니다.

현황과 다음 단계

지금은 로컬 데모 단계이고, 현장 엔지니어가 쓰고 있지는 않습니다. 그래프로 만든 도면은 하나뿐이고, 모든 수정은 한 번씩만 실행해 확인했습니다. reader 규칙이 EPLAN의 PDF 배치 방식에 기대고 있어서 템플릿이 다르면 오류 없이 깨질 수 있습니다. 엔지니어의 스키마 검토와 호스팅도 남아 있습니다.

일의 대부분은 파싱보다 그래프가 무엇을 주장해도 되는지 정하는 일이었습니다. 다음에는 시나리오 질문을 반복 실행하는 검사를 붙이고, 두 번째 도면으로 그래프를 만들고, 알람 코드 질문에 별도 경로를 주려 합니다.
