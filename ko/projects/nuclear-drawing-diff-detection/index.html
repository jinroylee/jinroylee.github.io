두산에너빌리티 원자력 기기 도면 변경점 검출 시스템

두산에너빌리티는 원자력 기기 도면의 두 개정본 사이에서 무엇이 바뀌었는지 자동으로 찾고 싶어 했습니다. 도면을 뷰, 표, 텍스트 영역으로 나누는 VLM Layout Detection 모듈을 개발하고 변경 검출의 지연 시간을 줄였습니다. PostgreSQL 작업 큐 위에 웹 앱도 구축했습니다. 현재 개발 중이며 곧 배포될 예정입니다.

  • −30%도면 쌍당 평균 비교 시간, 139초 → 97초 (22쌍 재실행)
  • 95.5%held-out 40쪽 Layout Detection 재현율 (F1 93.2)
  • 13→2표 136개 중 실패한 비교 (같은 세션 A/B)

픽셀 비교가 통하지 않는 이유

시스템은 변경마다 추가/삭제/수정 구분, 한 줄 설명, 두 도면 위의 위치 박스를 냅니다. 두 도면을 픽셀 단위로 비교해서는 이 결과를 얻을 수 없습니다.

  • 요소 이동: 개정 과정에서 뷰, 표, 주기가 자리를 옮기고, 도면 전체를 다시 그리기도 합니다. 위치만 바뀐 표는 변경이 아닙니다.
  • 세 종류의 내용: 뷰의 치수, 표의 셀, 주기의 문장은 바뀌는 방식이 달라서 비교 방법도 달라야 합니다.

그래서 파이프라인은 먼저 도면을 영역으로 나누고, 뷰는 뷰끼리, 표는 표끼리 비교합니다. 제 작업의 두 축도 이 구조에서 나왔습니다. Layout Detection은 영역을 빠짐없이 찾아야 하고, 변경 검출은 비교 한 번에 VLM 호출이 수십 번 일어나는 만큼 빨리 끝나야 합니다.

My contribution

4인 팀이고, 제 작업은 큰 축 두 가지와 작은 작업 하나입니다.

  • Layout Detection: 렌더링, VLM 호출과 prompt, 기하 후처리, 평가 설계까지 모듈 전체
  • 비교 지연 시간: 병목 분석, 결과를 바꾸지 못하는 작업 제거, 정확도 하한을 정해 둔 변경별 검증
  • 비교 작업 동시 처리: 전에는 사용자가 비교를 한 번에 하나씩만 돌릴 수 있었습니다. Next.js 웹 앱을 만들고 비교 작업을 PostgreSQL 작업 큐로 옮겨, worker가 여러 비교를 동시에 처리하게 했습니다.

변경 검출 에이전트의 아키텍처 설계에도 참여했습니다. 에이전트 구현, 영역 매칭, 정답 데이터 라벨링, 전체 파이프라인 평가는 팀원들이 했습니다.

Layout Detection: 영역을 빠짐없이 찾기

Layout Detection이 놓친 영역은 변경 검출 단계로 넘어가지 않습니다. 그래서 recall을 가장 중요한 목표로 잡았습니다.

엄격한 기준에서는 채점 방식을 바꿨습니다. 라벨러가 남기는 여백이 일정하지 않아서, 높이 10 pt 글자에서 여백이 3 pt만 달라도 IoU가 약 0.63으로 떨어집니다. 그래서 IoU를 계산하기 전에 두 박스 모두 여백을 잘라 냈습니다.

팀이 도면 16쌍으로 진행한 전체 파이프라인 평가에서, 놓친 변경 149건 중 Layout Detection 때문인 건 1건뿐이었습니다.

레이아웃은 VLM 한 번으로, 기하는 코드로

제약
뷰, 표, 주기를 가르려면 모양보다 도면 내용을 이해해야 하는 경우가 많습니다. 한 페이지는 60초 예산 안에 끝나야 했습니다.
검토한 대안
OpenCV 후보 중 선택, PDF 벡터와 텍스트 군집화, 사전학습된 Layout Detection 모델, 타일로 나눠 파싱/병합/검증하는 다단계 방식, VLM 한 번 호출 후 코드로 후처리.
선택
호출 한 번에 영역의 유형과 박스만 strict JSON schema로 받고, 글자는 옮겨 쓰지 않게 했습니다. prompt에는 정답 라벨링 규칙을 그대로 적어 검출 기준과 평가 기준을 맞췄습니다. 기하로 판단할 수 있는 일(3단계)은 코드가 합니다.
감수한 비용
후처리가 정답 데이터의 관례에 맞춰져 있어서, 관례가 바뀌면 같이 고쳐야 합니다. 모델이 오래 추론하는 페이지는 최대 약 76초까지 걸립니다.
결과
OpenCV 후보와 PDF 텍스트 레이어로는 목표 recall에 닿을 수 없었고, 다단계 방식은 추정치가 시간 예산을 넘었습니다.

남은 오류는 두 번째 호출 대신 예시와 잉크로

제약
남은 오류는 경계와 묶음 문제였습니다. 뷰 하나가 여러 영역으로 쪼개졌고, 텍스트 박스는 셀 테두리를 따라 그려지는데 정답 박스는 글자에 붙어 있었습니다.
검토한 대안
200 DPI로 잘라 다시 보내는 refinement pass, prompt의 묶음 규칙 구체화, 합칠 뷰만 판단하는 두 번째 호출, 예시와 결정적 보정.
선택
대상 페이지 앞에 예시 세 장을 넣었습니다. 올바른 뷰 박스와 묶는 이유를 적은 설명을 붙였고, 페이지 간에 캐시로 재사용합니다. 텍스트 박스는 코드로 보정합니다. 4,800 px로 렌더링해 셀 테두리 같은 긴 획을 지우고, 남은 글자를 줄 단위로 묶은 뒤, 박스를 그 줄들에 맞추고 최대 5 pt 여백을 줍니다.
감수한 비용
예시 때문에 입력 토큰이 약 23,000개, 페이지당 시간이 약 2.7초 늘었습니다. 정답 데이터가 쌓인 상세도를 페이지마다 다르게 묶은 경우가 있어서, 뷰 오류가 일부 남아 있습니다.
결과
124쪽을 두 번씩 실행했을 때 IoU 0.9 기준 F1이 84.1 → 88.5로 올랐습니다(+4.4, 95% CI 3.1~5.7). refinement pass는 힌트로 준 박스를 거의 그대로 돌려줬고, 구체화한 규칙과 별도 묶음 호출은 따로 둬야 할 뷰까지 합쳤습니다.

비교 지연 시간: 도면 쌍당 30% 단축

결과를 바꾸지 못하는 작업 덜어내기

제약
프로파일링해 보니 비교 시간의 약 90%가 변경 검출이었습니다. 영역은 병렬로 처리되므로 가장 느린 영역이 도면 쌍 전체 시간을 정하는데, 10쌍 중 6쌍에서 그 영역이 표나 뷰였습니다.
검토한 대안
16개 조합: 뷰의 모델 호출 상한 6/3/2/1회, 표 답변을 전체 셀로 받을지 바뀐 셀만 받을지, 비교할 수 없다고 표시한 표를 재시도할지 첫 답을 받을지.
선택
표는 모든 셀을 이유와 함께 다시 쓰는 대신 바뀐 셀만 답하게 했습니다. 모델이 비교할 수 없다고 표시한 표는 재시도하지 않고 첫 답을 받습니다. 기록을 보면 재시도로 결과가 바뀐 적이 한 번도 없었고, 원인은 이미지에 셀을 표시하는 방식에 있었습니다. 뷰는 모델 호출 상한을 6회 → 3회로 줄였습니다.
감수한 비용
가장 큰 표 두 개는 이제 120초 안에 답하지 못합니다. 전에는 그중 하나가 약 3분 만에 끝나 변경의 대부분을 찾았습니다.
결과
각 선택지는 recall 하락 2점 이하, F1 하락 3점 이하이고 신뢰구간이 더 큰 하락을 배제할 때만 받아들였습니다. 뷰 호출 상한 2회와 1회는 이 기준을 통과하지 못했습니다.

답을 짧게 해도 정확도는 떨어지지 않았습니다. 두 쪽 모두 끝까지 처리한 표 122개에서 F1은 똑같이 0.770이었고, F1 상승은 대부분 예전에 실패하던 표가 이제 답을 내면서 생긴 것입니다. 변경 검출은 LLM이라 실행마다 결과가 달라지고, 단일 실행 간의 작은 차이는 잡음일 수 있습니다.

회고

  • 지연 시간은 출력 토큰이 정합니다. 가장 싸게 빨라지는 방법은 아무도 읽지 않는 내용을 모델이 쓰지 않게 하는 것이었습니다. Layout Detection에서는 글자 옮겨 쓰기, 표 비교에서는 바뀌지 않은 셀이 그런 내용이었습니다.
  • 재시도는 실패가 무작위일 때만 도움이 됩니다. 이번 실패가 무작위가 아니라는 것은 프로파일링을 해 보고서야 알 수 있었습니다.
  • 배포 후에는 실제 부하에서 작업 큐를 측정하고, 가장 큰 표에만 더 긴 시간 제한을 주는 방법을 시험해 볼 계획입니다.
