도메인 지식을 코드 밖에 둔 이유

현장 엔지니어들은 같은 유형의 질문을 반복해서 했습니다. 질문 유형마다 어떻게 답해야 하는지는 코드가 아니라 도메인 지식입니다. 처음에는 이 지식이 에이전트 prompt 안에 있어서, 하나를 고치려 해도 개발자와 배포가 필요했습니다.

저는 이 구조가 어떤 에이전트든 시간이 지나면 무너진다고 봅니다. 현장 업무는 바뀌고, 새로운 질문 유형은 계속 생깁니다. 그러면 에이전트의 harness와 지식이 실제 업무와 점점 어긋납니다. 도메인은 개발자의 몫이 아니고, 도메인을 아는 사람은 대개 코드를 다루지 않습니다.

그래서 도메인을 아는 사람이 코드 밖에서 지식을 직접 관리할 수 있어야 한다고 판단했습니다. 에이전트도 이 분리를 기준으로 설계했습니다. 코드는 지식을 읽는 구조만 맡고, 지식은 도메인 담당자가 데이터로 고칩니다.

My contribution

멀티 에이전트 플랫폼은 현대자동차그룹이 구축하고 있고, 질의 에이전트는 MakinaRocks 팀이 만들었습니다. 질의 에이전트는 관계형 DB, 그래프 DB, 문서 레이크에서 데이터를 찾아 답하고, 그 안의 Text-to-SQL 에이전트가 플랫폼의 주력 에이전트입니다.

제가 설계하고 만든 것은 네 가지입니다.

  • Skill 체계: Text-to-SQL 에이전트의 skill 선택 middleware, PM이 skill을 관리하는 시스템
  • Harness agent: 플랫폼의 에이전트를 감싸는 오케스트레이터
  • PPTX subagent: harness agent의 슬라이드/보고서 도구 뒤에서 동작하는 에이전트
  • 평가 프레임워크: 에이전트를 채점하고 임계값으로 CI를 막는 라이브러리, CLI, API 서버

PM이 관리하는 skill

자주 들어오는 질문 유형을 사전 정의 skill 50개로 만들었습니다. Skill마다 언제 쓰는지 알려 주는 설명과, 어떻게 답할지 알려 주는 지침이 있습니다.

Skill은 prompt가 아니라 데이터로

제약
질문 유형별로 어떻게 답해야 하는지는 PM이 알고, 에이전트 코드와 배포는 개발자가 쥐고 있습니다.
검토한 대안
에이전트 prompt에 처리 규칙 작성, 질문 유형마다 처리 경로 하드코딩, 관리되는 skill 중에서 모델이 선택.
선택
Skill을 에이전트 코드 밖의 관리 데이터로 두었습니다. 내용은 PM이 고치고, 개발자는 선택 구조만 고칩니다.
감수한 비용
선택 품질은 설명 품질을 넘지 못합니다. Skill이 늘어날수록 PM이 설명끼리 구별되게 관리해야 합니다.
결과
PM이 개발자 배포 없이 자주 묻는 질문의 답변을 개선할 수 있습니다.

기능을 더하는 harness agent

Harness agent는 질의 에이전트 같은 플랫폼의 에이전트를 감싸고, 메모리, 문서 생성, 메시지 발송, 안전 검사를 더합니다. 그러면서도 단순 질문이 느려지면 안 됐습니다.

  • 단기 기억: 스레드 상태는 PostgreSQL checkpoint에 유지합니다. 루프의 context가 토큰 예산을 넘으면 오래된 도구 결과를 짧은 표시로 바꿉니다.
  • 장기 기억: 답변이 끝날 때마다 백그라운드 작업이 대화에서 사실과 선호를 뽑아 위키에 저장합니다. 사용자가 도구로 기억을 저장하거나 지울 수도 있습니다. 위키 검색은 pgvector를 쓰고 시간 제한이 있습니다. 메모리는 사용자, 에이전트 단위로 격리합니다.
  • Middleware chain: 모델을 호출할 때마다 middleware가 재시작 때문에 결과 없이 남은 도구 호출을 보정합니다. 위키 내용은 최신 사용자 메시지 바로 앞에 넣고, 도구 병렬 호출은 막습니다.

대화에서 바로 만드는 PPTX 보고서

사용자가 요청하면 harness agent가 대화 내용을 바로 PPTX 보고서로 작성합니다. 보고서 도구는 PPTX subagent를 호출합니다. 모델은 코드나 XML을 직접 쓰지 않습니다. 슬라이드 레이아웃 13종과 차트 30종의 타입 스펙만 채우고, python-pptx 빌더가 PPTX 템플릿 위에 그립니다. 구조 검사가 레이아웃 오류를 필드, 한도와 함께 도구 결과로 돌려주면 모델이 스스로 고칩니다.

생성 시간을 줄이려고 도구와 모델 호출 횟수를 줄였습니다. 지금은 페이지를 병렬로 작성하고, 거절된 페이지만 다시 시도합니다.

에이전트마다 CI에서 돌리는 평가

플랫폼의 각 에이전트 팀은 배포 전에 CI에서 자기 에이전트를 검증해야 합니다. 제가 만든 평가 프레임워크는 설정 파일과 정답 데이터셋만 추가하면 쓸 수 있고, 지금은 플랫폼 여러 에이전트의 CI pipeline에 들어가 있습니다.

  • 지표: RAG, Text-to-SQL, 공통 품질 3개 그룹, 14개 지표
  • 설정: YAML 파일 하나로 LangGraph 그래프 지정, 최종 상태를 공통 필드에 매핑, 지표별 임계값 설정
  • 게이트: 통과 0, 게이트 실패 1, 설정 오류 2로 종료
  • 제공 형태: CLI, metric endpoint 12개를 갖춘 FastAPI 서버, Docker 이미지

객관적 정답은 코드로, 주관 품질만 judge로

제약
LLM judge는 객관적인 과제에서 믿기 어렵고, 큰 SQL 결과셋은 judge prompt에 다 들어가지 않습니다. 정답 데이터셋도 작습니다.
검토한 대안
모든 답변을 LLM으로 채점, SQL 문자열 비교, 결과셋과 검색 문서 ID를 코드로 비교.
선택
객관적인 답은 코드로 확인합니다. Text-to-SQL은 예측 결과셋과 정답 결과셋의 (컬럼, 값) 사실 단위 Soft F1로, RAG는 검색한 문서 ID를 정답 ID와 비교해 판정합니다. Judge는 주관 품질과 근거성만 채점합니다. 표본이 작아서 리포트에는 Wilson 신뢰구간, cluster-robust 표준오차, bootstrap p95를 함께 냅니다.
감수한 비용
항목마다 정답 결과셋을 준비해야 합니다. 맞는 SQL이라도 결과 형태가 다르면 점수가 낮게 나옵니다.
결과
정답성 통과 여부를 재현할 수 있고, 모델 판단에 좌우되지 않습니다.

한계와 다음 단계

라우팅 정확도, harness agent가 더하는 지연 시간, skill이 답변에 준 효과는 측정하지 않았습니다. 도구가 필요 없는 턴 70%라는 비율도 설계상 추정치이지 측정값이 아닙니다.

루프 안의 도구는 harness 상태를 잃으면 마지막으로 쓴 설정으로 되돌아갈 수 있습니다. 동시 사용 중에는 이 때문에 한 스레드의 설정이 다른 스레드로 넘어갈 수 있습니다.

다음 단계로 두 가지를 제안합니다. 첫째, CI 게이트를 점추정값이 아니라 신뢰구간 하한에 걸어야 합니다. 둘째, PPTX 루프에 렌더링 검사를 넣어야 합니다. 지금은 렌더링된 슬라이드를 보는 단계가 없어서, 구조 검사가 놓친 문제가 그대로 사용자에게 갑니다.
