주성엔지니어링 폐쇄망 실험 보고서 검색 에이전트

주성엔지니어링의 공정 실험 결과는 표와 수치가 대부분인 슬라이드 보고서로 남아 있고, 엔지니어들은 폐쇄망 안에서 이 보고서에 질문할 수 있기를 원했습니다. vLLM으로 LLM과 VLM을 서빙하고, 보고서 표를 헤더로 찾아갈 수 있는 셀 데이터로 구조화하고, 검색 에이전트를 개발했습니다. 고객사 직원들이 실제 업무에 사용했습니다.

  • 20 TB슬라이드 보고서 적재, 약 1주 반 (기존 방식 예상 약 2개월)
  • ~150/h시간당 적재한 보고서 파일 (기존 10~20개)
  • 2폐쇄망에 vLLM으로 서빙한 모델 (120B LLM, 30B VLM)
역할
LLM 서빙, 표 구조화, 적재 아키텍처, 실험 보고서 검색 에이전트

폐쇄망 안에 올린 전체 스택

주성엔지니어링은 반도체, 디스플레이, 태양전지 제조 장비를 만드는 회사입니다. 마키나락스는 정부 지원 과제로 실험 보고서와 인사규정 질문에 답하는 에이전트를 만들었습니다.

고객사 네트워크는 인터넷이 없는 폐쇄망입니다. 외부 모델을 호출하거나 패키지를 내려받을 수 없어서, 모델, DB, 서비스 전부를 고객사 Kubernetes 클러스터와 정해진 GPU 위에서 돌려야 했습니다. 그 안에서 LLM 서빙부터 배포까지 전체 스택을 둘이서 구축했습니다.

My contribution

팀원 한 명과 둘이 진행했고, 제가 맡은 부분은 아래와 같습니다.

  • 서빙과 플랫폼: 두 모델의 vLLM 서빙, VDB, RDB, Object Storage와 배포 환경을 폐쇄망 클러스터에 구축
  • 구조화: DDL 스키마 설계, 파싱된 슬라이드의 표를 헤더 경로가 붙은 행으로 바꾸는 변환 로직, VLM 이미지 설명 추출
  • 적재: 큐/worker 구조 설계, 파이프라인 전체 튜닝
  • 검색: 에이전트의 실험 보고서 검색 경로 개발

슬라이드 파싱, NAS 스캔/복호화/중복 검사, 인사규정 에이전트, 오프라인 반입 패키징, 채팅과 관리 기능은 팀원이 개발했습니다.

슬라이드 보고서의 구조 읽기

스키마를 설계하기 전에, DRM이 걸린 NAS에 수년 치 쌓인 슬라이드 파일이 의미를 어떻게 담고 있는지부터 살펴봤습니다. 설계를 좌우한 특징은 세 가지였습니다.

  • 레이아웃: 레이아웃이 자유롭습니다. 표 하나를 손으로 둘로 나눠 놓거나 표 셀 위에 그래프 이미지를 얹은 슬라이드가 많습니다.
  • 의미: 대부분 표와 수치입니다. 값은 행/열 헤더가 있어야 의미가 생기는데, 양쪽 축 모두 헤더가 여러 단으로 중첩된 경우가 흔합니다.
  • 질문: 엔지니어는 주제가 아니라 조건으로 묻습니다. 예를 들면 “이 증착 실험에서 압력을 X로 설정한 적이 있어?” 같은 질문입니다.

답은 맞는 슬라이드의 맞는 셀에서 나와야 했습니다. 설계 원칙은 하나였습니다. 판단은 LLM이 하고, 구조는 코드가 만듭니다.

헤더 경로로 셀 찾아가기

제약
셀 하나가 의미를 가지려면 전체 헤더 경로가 필요한데, 표 레이아웃은 슬라이드마다 달랐습니다.
검토한 대안
표를 마크다운 그대로 슬라이드 텍스트에 넣어 색인, LLM으로 표마다 고정 스키마에 맞춰 변환, 셀을 헤더 경로와 함께 저장.
선택
LLM은 어느 행과 열이 헤더인지만 판단합니다. “압력 > 챔버” 같은 헤더 경로는 코드가 만들고, 표의 경로 목록을 카탈로그로 저장한 뒤 모든 셀에 행 경로와 열 경로를 하나씩 붙입니다. 가장 중요한 두 표 유형인 레시피, run sheet는 LLM 없이 규칙 기반 휴리스틱으로 나눠 step/run 단위 레코드로 저장합니다.
감수한 비용
일반 표는 여전히 LLM의 헤더 판단에 의존합니다. 슬라이드에서 참조되지 않은 표에는 도달할 수 없고, 휴리스틱은 지금까지 본 형식에만 맞춰져 있습니다.
결과
검색 단계에서 질문에 맞는 헤더 경로를 고른 뒤 그 셀만 읽습니다.

벡터 검색이 약했던 지점

보고서에 나오는 공정 용어와 단위의 폭이 좁아서, 쿼리 하나로 검색하면 비슷한 슬라이드가 수십 장씩 나왔습니다. 같은 장비와 조건을 순서만 바꿔 물었는데 전혀 다른 슬라이드가 나오는 경우도 있었습니다.

그래서 먼저 검색 결과를 안정시켰습니다. LLM이 질문을 장비, 막 같은 다섯 가지 식별 요소와 조건으로 분해하고, 변형 쿼리는 식별 요소에 정해진 규칙을 적용해 만듭니다. 변형 쿼리마다 나온 하이브리드 검색 결과는 RRF로 합칩니다. 이제 표현이 달라도 식별 요소가 같으면 같은 쿼리 묶음으로 검색합니다. 그 대신 질문마다 LLM 호출이 하나 늘었습니다.

Run sheet 질문은 Text-to-SQL 두 번으로

제약
run sheet는 한 행이 실험 run 하나이고, 질문은 “350 °C 초과, 5 Torr인 run”처럼 수치로 거릅니다. 벡터 유사도로는 ‘초과’를 판단할 수 없습니다.
검토한 대안
셀 대상 벡터 검색, 전체 스키마 대상 Text-to-SQL 한 번.
선택
run 하나를 한 행으로 저장하고, 각 셀에는 표 카탈로그의 헤더 경로를 붙입니다. 첫 번째 쿼리로 조건에 맞는 run을 고르고, 두 번째 쿼리로 막 두께처럼 질문이 요구한 셀만 가져옵니다.
감수한 비용
LLM 호출이 두 번 들고, 정확도는 헤더 카탈로그 품질에 좌우됩니다. 이 경로는 run sheet에만 씁니다.
결과
수치 조건은 모델이 아니라 DB가 계산합니다.

권고안: 수치 위주이고 쓰이는 어휘가 좁은 보고서에서는 벡터 검색이 주 검색 수단으로 맞지 않습니다. 그래서 표와 Text-to-SQL을 주 경로로 두고 벡터 검색은 보조로 쓰자는 권고안을 작성했습니다. 표 데이터는 고객사의 실험 관리 소프트웨어에서 가져오거나, 보고서를 더 일정한 스키마로 적재해 만들 수 있습니다.

테스트로 병목 찾기

보고서 원본은 PPTX 파일 약 20TB였고, 처음 만든 적재 구조로는 이 양을 감당하기 어려웠습니다. 실제 보고서로 파이프라인을 돌려 병목을 하나씩 찾고, 원인이 된 계층을 고쳤습니다. 손본 계층은 Kubernetes pod 구조, worker의 멀티프로세싱/멀티스레딩, vLLM 서빙 옵션입니다.

적재를 단계별 worker로 분리

제약
파일 하나를 단일 프로세스로 처리하고 LLM 호출만 멀티스레딩하는 방식은 너무 느렸고, 여기에 LibreOffice로 슬라이드를 캡처하는 작업까지 붙었습니다. 멀티프로세싱을 늘리자 OOM과 DB 커넥션 풀 초과가 났습니다.
검토한 대안
한 서비스 안에서 프로세스/스레드 수 조정, 단계별로 작업 분리.
선택
CPU를 많이 쓰는 작업(슬라이드 렌더링)과 지연 시간이 긴 작업(LLM 호출)을 메인 worker에서 떼어 별도 pod로 옮겼습니다. 큐 네 개를 체인으로 이었습니다. 파싱 worker는 구조화 결과를 디스크에 쓰고, 별도 적재 컴포넌트 하나가 이를 모아 PgBouncer를 거쳐 PostgreSQL에 배치로 넣습니다.
감수한 비용
제대로 된 메시지 브로커가 없고 큐 계층이 얽혀 있습니다.
결과
단계마다 따로 확장할 수 있고, DB 쓰기는 모든 파싱 프로세스가 아니라 적재 컴포넌트 하나만 거칩니다.

OOM killer가 남긴 프로세스 정리

단계를 나눈 뒤, 오류를 낸 작업이 없는데도 worker 메모리가 시간이 갈수록 늘었습니다. 메모리 추이와 서버 로그를 맞춰 보니 OOM killer에 걸린 프로세스가 오류 없이 고아 프로세스로 남아 메모리와 다른 자원을 계속 쥐고 있었습니다. 이런 고아 프로세스를 찾아 정리하는 memory sweeper를 추가했습니다. sweeper는 증상만 처리합니다. 고아 프로세스를 만드는 렌더링의 중첩 서브프로세스 구조는 그대로 남아 있습니다.

vLLM 서빙 옵션 조정

적재 부하와 에이전트 응답 지연을 기준으로 아래 옵션을 정했습니다.

결과

처리량은 시간당 보고서 파일 약 10~20개 → 약 150개로 늘었습니다. 2년 치 보고서를 약 1주 반 만에 적재했습니다. 기존 속도로는 약 2개월이 걸릴 것으로 추정했던 양입니다.

한계와 회고

검색이나 답변 정확도는 측정하지 않았습니다. 위 처리량은 파이프라인 전체 수치라 변경 하나하나의 효과는 따로 재지 않았습니다. 답변 품질은 정성적으로만 확인했고, GPT-OSS-120B가 system prompt를 잘 따르지 않았습니다.

온프렘 LLM이라 토큰 비용 걱정은 없었지만, 대신 지연 시간이 큰 부담이었고 답변의 충실성도 보장되지 않았습니다. 그래서 결정적인 로직으로 처리할 수 있는 부분은 코드에 맡기고, LLM은 꼭 필요한 곳에만 써야 한다는 것이 가장 큰 교훈이었습니다. 다음에는 첫 worker를 만들기 전에 자원과 병렬 처리부터 설계하려 합니다.
